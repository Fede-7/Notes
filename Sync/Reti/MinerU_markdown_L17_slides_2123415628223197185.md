## [Remind] Responsibilities of Transport Layer

Everything so far assumed the connection was already there: buffers, variables, two numbers counting bytes. 

• At the connect/accept, the two ends must agree that they are talking, and on the number each will count from. 

• At the end, the two ends should stop without leaving one side talking to a peer that has gone. 

• Nothing new is needed in the header — three flag bits (SYN, ACK, FIN) do all of it. 

• Of the four things transport does (multiplex/demultiplex, reliability, flow and congestion, connection), this is the one your own code has been asking for all along: connect, accept, close. 

# Transport Layer [Recall] TCP Segment

• The TCP segment consists of header fields and a data field, the latter contains some application data of at most MSS size. 

• The header contains several fields: 

• Sequence number (32-bit) for reliable data transfer. 

• Acknowledgment number (32-bit) for reliable data transfer. 

• Receive window (16-bit) used to indicate the number of bytes that a receiver is willing to accept (for flow control). 

• Header length (4-bit) specifies the number of 32-bit words contained into the header. Note that TCP header is variable due to the options field. 

• Options field (K-bit) used for optional processes such as negotiating the MSS, time-stamping, etc. 

• Flags (6/12-bit) including: 

• ACK bit indicates that this segment is an ACK packet (so the acknowledgment number field is in use). 

• RST, SYN, and FIN bits used for connection setup and teardown. 

• CWR and ECE bits used in explicit congestion notification (optional). 

• PSH bit tells the receiver to pass the data to the application immediately. 

• URG bit indicates that the segment contains “urgent” data. 

• Checksum (16-bit): for integrity check. 

• Urgent data pointer field (16-bit) indicates the location of the last byte of the urgent part of the data.

## Transport Layer [Recall] TCP Segment: three bits

• SYN: this segment opens a connection. It is set in the first two segments of a connection and never again. 

• FIN: the sender has no more data. It closes one direction, and is sent once per direction. 

• RST: there is no connection here. Throw the segment away and do not send it again. 

• The sequence and acknowledgement fields carry the agreement; these three bits say what kind of agreement it is.

## Transport Layer TCP Problems in Connection Management

• Since TCP is connection-oriented two hosts must agree during both the opening and the closing procedures. 

• Knowing that messages could be lost or damaged on the network, it is quite difficult for two hosts to find such agreement. 

• If messages are lost during transmission one end of the communication can be open or closed while the other is not. 

• To avoid (or mitigate) this issue TCP implements a procedure called three-way handshake in which open/close connection requests have to be acknowledged by hosts before a connection can be established/released.

# Transport Layer TCP Problems in Connection Management

## What is impossible:

In an unreliable network, no finite exchange of messages can guarantee that both endpoints know with certainty that the other has completed the exchange. 

• What TCP needs is weaker: each end has learnt the other’s initial number, and knows its own was received. 

• Three segments deliver exactly that, and nothing in them has to be believed on faith — each is confirmed by the next. 

• The doubt that remains is the sender’s about his last message. Subsequent data exchange can implicitly confirm that the server has established the connection. 

• Uncertainty about the final ACK matters during connection termination, where TCP uses the TIME_WAIT timer to handle it. 

## Transport Layer TCP Connection Establishment

• In TCP three-way handshake is performed to establish connection: 

• Client sends a connection request (SYN segment: SYN bit set and no data) to the server. 

• Server responds with a special acknowledgment (SYNACK segment: SYN and ACK bit set). 

• Client sends back a final acknowledgment (ACK segment), and this third segment may already carry application data. 

• TCP connection establishment is a delicate procedure that can also add significantly delays. 

• There is typically a timeout (30-60 secs) to complete the handshake, after that the procedure is aborted. 

• Some attacks (e.g., SYN flood) happen here.

## Transport Layer TCP Connection Establishment

• Details of the three-way handshake procedure: 

1. The client sends a SYN segment having: 

• No application-layer data (payload). 

• The SYN bit set to 1. 

• A random initial sequence number (client_isn) as sequence number. 

2. When the above SYN segment (hopefully) arrives, the server allocates TCP buffers and variables and sends back a SYNACK segment having: 

• No application-layer data (payload). 

• The SYN and ACK bits set to 1. 

• The acknowledgment number set to client_isn+1. 

• A random initial sequence number (server_isn) as sequence number. 

3. When the SYNACK segment (hopefully) arrives, the client also allocates buffers and variables to the connection and sends to the server a final ACK segment having: 

• Possibly application-layer data. 

• The SYN bit set to 0 (connection is established) and ACK bit set to 1. 

• The acknowledgment number set to server_isn+1.

## TCP: Why the initial numbers are drawn at random

Nothing forces a connection to start at zero, and starting there would be a bad choice: 

• A segment from an earlier connection between the same four numbers may still be wandering in the network. 

• With a fresh starting point it falls outside the window of the new connection and is discarded instead of accepted as data. 

• An attacker who can guess the numbers can inject segments into a connection he cannot see: randomising them is a defence. 

• And the +1 coming back is a small proof of its own: only somebody who received the SYN could have written it.

## Transport Layer TCP Connection Establishment

• listen is the transition into LISTEN. From that instant the kernel answers SYNs by itself, with no process involved. 

connect sends the SYN and blocks; it returns when the SYNACK has arrived and the third segment has been sent. 

• accept takes no part in the handshake at all: it hands you a connection that is already established. 

• So a server can be slow to call accept without any client noticing — the connection is open, and the data waits in a buffer. 

• The handshake is done by the two kernels. Your program reads the result, and its only report is a descriptor or an error. 

## Transport Layer TCP Connection Establishment: two queues

A listening socket has a queue of half-open connections — SYN received, third segment not yet — and a queue of completed ones waiting to be accepted. 

• An arriving SYN creates an entry in the first queue; the final ACK moves that entry into the second. 

• accept removes one entry from the second queue: the backlog you passed to listen is that queue’s length. 

• If it fills up, new connections are dropped or refused, and the client sees a delay without ever learning the reason. 

• The SYN queue is a potential target for SYN flood attacks, which can be mitigated using SYN cookies. 

## Transport Layer TCP Connection Establishment

Before the first byte of a request leaves, one full round trip has already been spent on agreeing to talk. 

• On a local network that is nothing. Across an ocean it is a tenth of a second, per connection. 

• This is exactly what persistent connections buy at the application layer: pay the handshake once, and reuse what it built. 

• It costs the server too: buffers and variables are committed on the first segment, before anything has been asked of it. 

# Transport Layer TCP: Nobody answers, or somebody refuses

## Your client calls connect and the SYN gets no answer. How long does it wait?

Tens of seconds. TCP retransmits the SYN a few times with a growing interval, then abandons the attempt and connect fails (connect() = -1 and errno = ETIMEDOUT). 

## A refusal is much faster:

if the host is up but nothing is bound to that port, it replies with a segment carrying RST = 1 (connect()= -1 e errno = ETIMEDOUT). 

In summary: your program sees the two as different errors — a timeout, or the ECONNREFUSED you got the first time you started the client before the server. 

For UDP that report came from the network layer instead. Here the answer is a transport segment, from the peer’s TCP. 

# Transport Layer TCP: SYN flood

## What if the third segment never comes?

The server has already committed buffers and variables. It holds the half-open connection for a minute or more before reclaiming it. 

• Send enough SYNs and the queue of half-open connections is full of entries that will never complete. 

• Legitimate clients are then refused: what has been exhausted is a queue, not bandwidth — the attack needs very little traffic. 

• The source addresses are forged, so the SYNACKs go to hosts that never asked, and the attacker never has to reply. 

• It was among the first documented denial-of-service attacks, and it is still one of the most common. 

## SYN cookies protect against SYN flood attacks by avoiding resource allocation for incomplete connections.

• Normally, the server stores each half-open connection in the SYN queue. 

When the SYN queue becomes full, the server can enable SYN cookies and respond without storing connection state. 

The server computes a cookie using a hash of the IP addresses, ports, a secret key and time information. 

• The cookie is encoded in the initial sequence number (ISN) of the SYN-ACK. 

When the final ACK arrives, the server validates the cookie and only then allocates resources for the established connection.

## Transport Layer TCP Connection Release

• TCP connection release (aka teardown) can be performed by either host. 

• Let’s assume client is closing the connection, the three-way handshake is performed as follow: 

1. The client sends a special shutdown segment (FIN segment) to the server having the FIN bit set to 1. 

2. When the server receives this segment, it sends back an acknowledgment/shutdown segment, having ACK to 1 and FIN bit set to 1. 

• Note: ACK and FIN can be sent in the same segment or in two separated ones. 

3. Finally, the client acknowledges the server’s shutdown segment.

## Transport Layer Half-close: one direction at a time

• A FIN says I have no more data to send. It does not say this connection is over: it closes one direction. 

• After sending its FIN the client can still receive; after acknowledging it the server can still send, for as long as it likes. 

• So the two FINs are independent, and the normal release is four segments: FIN, ACK, then FIN, ACK the other way. 

• They collapse into three only when the peer has nothing left to send and closes at once: then its ACK and its FIN travel together. 

• close sends the FIN and gives up the descriptor. shutdown(fd, SHUT_WR) sends it and keeps reading — which is how a client says that was the whole request.

## TIME-WAIT

The end that closes first does not go straight to CLOSED. It waits — typically thirty seconds to two minutes. 

• First reason: if its last acknowledgement is lost, the peer will resend its FIN, and somebody has to be there to answer. 

• Second reason: segments of this connection may still be in the network, and its four numbers could be handed to a new one. 

• The wait is about twice the longest a segment can survive, so everything belonging to the old connection has died first. 

• It is the price of closing first, and it is paid by whoever closes first — which is not always the client. 

## You interrupt your server, restart it, and bind fails. Nothing else is running. Why?

Because interrupting it made it the end that closed first. Its connections are in TIME-WAIT, still holding the local port, and bind will not take a port that a live connection is using. 

• SO_REUSEADDR says bind anyway. 

• It is safe: the old connection keeps its four numbers, and no segment of it can be delivered to the new socket. 

• When the client closes first, which is the usual case, the server never enters TIME-WAIT and the problem never appears. 

# Transport Layer The descriptor nobody closed

## Your server’s recv returns 0 and you forget to close the descriptor. What breaks?

Nothing, at first. The connection stays in CLOSE-WAIT for ever: the peer’s FIN was acknowledged, but your FIN is never sent. 

• The peer is left waiting too. The release never finishes on either side, and neither program is told. 

• A few thousand clients later the server is out of descriptors and stops accepting. The failure appears far from its cause. 

• ss -tn state close-wait lists exactly those. A column of CLOSE-WAIT is always a bug in the program, never in the network. 

• That 0 is the FIN arriving. It is an instruction to close, not an error to ignore.

# Transport Layer TCP: Connection Reset (RST)

Unlike FIN, which supports graceful connection termination, RST immediately aborts a TCP connection, potentially discarding buffered data. 

• RST generation: A host sends an RST when it receives a segment for a nonexistent TCP connection (e.g., a SYN to a closed port). 

• Host crash: A crashed host sends neither FIN nor RST. The peer may therefore continue to consider the connection established. 

• After reboot: If the peer sends data to the restarted host, which has lost the connection state, the host responds with RST. 

• Application errors: A received RST may result in ECONNRESET. Subsequent writes may fail with EPIPE and generate SIGPIPE. 

• Failure detection: TCP detects unresponsive peers through retransmission timeouts or optional keepalive probes. Applications requiring faster failure detection can use periodic heartbeats.

## Summary

• Agreement over a channel that loses messages cannot be made certain. Three segments are not a proof; they are enough. 

• The handshake trades two random initial numbers and commits state on both sides: one round trip before any data moves. 

• A close is two independent halves, a FIN each way, each acknowledged. Recv returning 0 is the peer’s FIN. 

• TIME-WAIT protects the last acknowledgement and the four numbers; a CLOSE-WAIT that never ends is your own bug. 

• RST is the refusal — no such connection here — and timers close what agreement cannot. 

• Still open: the receive window in the header, and what a sender does when the limit is not the receiver but the network.

## Application Layer Creating Network Applications

• So far, we have looked at several network applications and protocols, we will now see how to create network applications. 

• Most network applications include a client-side program and a server-side program that communicate through the network. 

• When these two programs are executed, a client process and a server process are created, and these processes communicate with each other by reading from, and writing to, sockets. 

## Application Layer Creating Network Applications

## • Choice of protocols:

• Open protocols. Protocols whose rules are public, so anyone can write either side and the two will interoperate. 

• Proprietary protocols. “Custom” protocols (not been openly published in an RFC or elsewhere). One team writes both sides and controls the format, and nobody else can write a program that talks to it. 

## • Examples:

• A browser from one vendor talks to a server from another because both follow the same published rules. 

• An open protocol should use its well-known port; your own protocol must stay away from those.

## Socket

• A socket is one end of a two-way communication channel between two processes, referred to by a descriptor. 

• Introduced in BSD 4.2 in 1983, and still the de facto standard: Unix, macOS, and Windows with a different spelling. 

• The two processes may be on the same machine or on two machines across the world: the calls do not change. 

• It is not tied to TCP/IP. The same API served other protocol families, and it is why the calls look generic. 

• Being a descriptor, it accepts read, write and close — the calls you already know.

## Application Layer UDP and TCP

• UDP and TCP sockets implement the previous procedure to allow connectionless and connection-oriented communication, respectively. 

• The basic APIs providing UDP and TCP sockets are typically available in almost all programming languages and operating systems: • C, C++, C#, Java, Perl, Python, Matlab, etc. 

• The underlying implementation and the usage depends on the configuration of the machines. 

• In Unix domain we use Berkeley sockets (aka BSD or POSIX sockets) for both TCP and UDP connections. These are native C APIs.

## Sockets: Creation

• Sockets are created in C by using the socket() function: 

#include <sys/socket.h> 

int socket(int domain, int type, int protocol); 

## Where:

• domain: specifies the network domain and addressing family (e.g., AF_INET for IPv4). 

• type: specifies the communication semantics (e.g., stream or datagram). 

• SOCK_STREAM -> TCP socket 

• SOCK_DGRAM -> UDP socket 

• protocol: specifies a particular protocol to be used. 

• This is often 0 for the default protocol. 

• sockfd: is the file descriptor that identifies the newly created socket. 

• Notice that sockets adhere to the Unix philosophy that “everything is a file” where I/O sources are treated as files (and associated to a file descriptor).

## Sockets: Binding

• We can associate a socket to local address and port by using the bind() function: 

#include <sys/socket.h> 

int bind(int socket, const struct sockaddr *address, socklen_t address_len); 

## Where:

• socket: is the file descriptor of the socket we want to bind. 

• address: pointer to a sockaddr structure specifying on which port and address to bind. 

• address.sin_addr often set to INADDR_ANY so connections from all addresses are listened (multiple IPs). 

• address_len: specifies the length of the sockaddr structure pointed to by the address argument (we can use sizeof() to get it). 

• val: return value which is 0 on success, and -1 otherwise. 

• Notice that this function is used on servers as we must bind the socket to a specific port but is optional on clients (the OS assigns a free port automatically).

## Sockets: UDP

UDP (User Datagram Protocol) is a simple transport-layer protocol. Unlike TCP, which is connection-oriented, UDP does not establish a connection between client and server and does not provide reliability guarantees. 

While TCP transmits a stream of bytes, UDP sends discrete packets called datagrams. 

Because UDP does not require connection establishment or termination handshakes, it introduces less overhead than TCP and can be faster for transmitting small amounts of data. 

Transmission errors and packet loss are relatively infrequent in many networks, so when occasional data loss is acceptable, UDP can provide very fast and efficient communication. 

## Sockets: Send and Receive (UDP)

## • Processes of sending or receiving messages in UDP are performed by the sendto() and recvfrom() functions:

#include <sys/socket.h> 

int ob = sendto(int osock, const void *obuf, size_t olen, int oflags, const struct sockaddr *oaddr, socklen_t oaddr_len); 

#include <sys/socket.h> 

int ib = recvfrom(int isock, void *ibuf, size_t ilen, int iflags, struct sockaddr *iaddr, socklen_t *iaddr_len); 

## Where:

• osock/isock: are the file descriptors on which to send/receive a message. 

• obuf/ibuf: are pointers to the buffers containing a message to send/receive. 

• olen/ilen: are lengths of the messages in bytes. 

• oflags/iflags: specifies flags (typical values are 0 or MSG_WAITALL to wait until all olen/ilen bytes are sent/received). 

• oaddr/iaddr: pointers to sockaddr structures containing the receiving/sending address. 

• oaddr_len/iaddr_len: length in bytes of the sockaddr structure. 

• ob/ib: number of bytes that are actually sent/received. 

## Sockets: Send and Receive (UDP)

ssize_t sendto(int sockfd, const void *buf, size_t len, int flags, const struct sockaddr *dest_addr, socklen_t addrlen); 

## • Return value:

• Number of bytes sent, or -1 on error. 

Blocking: By default, sendto() may block until the datagram is accepted by the OS. It does not wait for delivery to the receiver. MSG_DONTWAIT prevents blocking. 

## • Parameters:

• sockfd: socket descriptor. 

• buf: pointer to the data buffer to be sent. 

• len: number of bytes to send. 

• flags: controls the sending behavior: 

• 0: default behavior. 

• MSG_DONTWAIT: performs a non-blocking send operation. 

• dest_addr: pointer to the destination address structure. 

• addrlen: size of the destination address structure (in bytes). 

## Sockets: Send and Receive (UDP)

ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags, struct sockaddr *src_addr, socklen_t *addrlen); 

• Number of bytes received, or -1 on error. 

• Parameters: 

Blocking: By default, recvfrom() blocks until a datagram is available. To avoid waiting indefinitely, use MSG_DONTWAIT or configure a receive timeout (SO_RCVTIMEO). 

• sockfd: socket descriptor. 

• buf: pointer to the receive buffer. 

• len: maximum number of bytes to receive. If the datagram is larger than the buffer, excess bytes are normally discarded. 

• flags: controls the receiving behavior: 

• 0: default behavior. 

• MSG_PEEK: reads a datagram without removing it from the receive queue. 

• MSG_DONTWAIT: performs a non-blocking receive operation. 

• src_addr: pointer to a structure that stores the sender's address. 

• addrlen: pointer to the address structure length (in bytes).

## Sockets: Implicit Binding (UDP)

When a UDP socket is created with socket(), it is not yet bound to a local port. 

• If the client calls sendto() without first calling bind(), the operating system automatically assigns an available local port (implicit binding). 

• The source IP address is selected according to the network interface and routing configuration. 

• The assigned port remains associated with the socket until it is closed. 

• A subsequent call to bind() on the same socket fails because the socket is already bound. 

Note: implicit binding does not establish a connection between the client and the server.

## UDP: Server and Client Start-up Order

## Case 1: Client starts before Server

• The client sends a datagram using sendto(). 

• If a UDP datagram reaches the destination host but no socket is bound to the destination port, the UDP layer discards the datagram. An ICMP Port Unreachable message may be generated. 

• When the server starts, it cannot retrieve the lost datagram. 

• The client may remain blocked on recvfrom() or receive an error (e.g., ECONNREFUSED). 

## Case 2: Server starts before Client

• The server calls bind() and waits on recvfrom(). 

• The client starts and sends a datagram. 

• The server receives the datagram and sends a reply. 

• The client receives the reply. 

Note: UDP does not buffer datagrams for applications that are not listening. Lost datagrams are not automatically retransmitted. 

## UDP: Receive Timeout

By default, recvfrom() is a blocking operation: it waits until a datagram is received or an error occurs. 

A receive timeout can be configured using setsockopt() with the SO_RCVTIMEO option. 

Example: timeout 

struct timeval timeout; 

timeout.tv_sec = 5; 

timeout.tv_usec = 0; 

setsockopt(sockfd, SOL_SOCKET, SO_RCVTIMEO, 

&timeout, sizeof(timeout)); 

## Behavior:

• If a datagram arrives before the timeout, recvfrom() returns the received data. 

• If no datagram arrives within 5 seconds, recvfrom() returns -1, with errno set to EAGAIN or EWOULDBLOCK. 

• The timeout does not retransmit lost datagrams. 

## UDP: Communication with Multiple Clients

## UDP does not require a connection to be established between the client and the server.

• A UDP server uses a single socket bound to a known port. 

• Multiple clients can send datagrams to the same server socket. 

• Each recvfrom() call receives a datagram and provides the sender's IP address and port number. 

• The server uses sendto() to send a reply to the corresponding client. 

• No listen(), accept(), or separate socket for each client is required. 

Note: A UDP server can communicate with multiple clients using a single socket, without establishing connections.

UDP sockets have two kernel-managed buffers: a send buffer for outgoing datagrams and a receive buffer for incoming datagrams. 

## Sending — sendto()

• The send buffer size can be configured using SO_SNDBUF. 

• Each sendto() call sends a complete UDP datagram. 

• Blocking socket (default): if insufficient buffer space is available, sendto() may block until the datagram can be accepted. 

• Non-blocking socket: sendto() returns immediately; if the datagram cannot be accepted, it returns -1 with EAGAIN or EWOULDBLOCK. 

UDP does not support partial datagram sends: the complete datagram is accepted or the operation fails. 

# Sockets UDP: Buffer

UDP sockets have two kernel-managed buffers: a send buffer for outgoing datagrams and a receive buffer for incoming datagrams. 

## Receiving — recvfrom()

• The receive buffer size can be configured using SO_RCVBUF. 

• Incoming datagrams are queued in the socket's receive buffer. 

• Blocking socket (default): recvfrom() blocks if no datagram is available. 

• Non-blocking socket: recvfrom() returns immediately with EAGAIN or EWOULDBLOCK if no datagram is available. 

• Each recvfrom() retrieves at most one datagram. 

If the application buffer is smaller than the received UDP datagram, the datagram is truncated: the excess bytes are discarded and cannot be retrieved by subsequent receive calls. 

## Socket: From UDP to TCP

• Unlike UDP, in TCP client and server need to handshake before messages can be transmitted. 

## • We use two sockets on the server-side:

• A welcoming socket, which is always on, and allows clients to perform handshakes with the server. 

• A client-specific socket, which is created after the handshake, and is used by client and server to communicate. 

• The three-way handshake, which takes place within the transport layer, is completely invisible to the client and the server programs. 

• Once the connection is accepted by the server (handshake success) the communication moves to the newly created socket.

# Sockets: Options SO_REUSEADDR

• SO_REUSEADDR is a socket-level option (SOL_SOCKET). 

• It allows a local address and port to be reused under certain conditions, particularly when previous TCP connections are in TIME_WAIT. 

• The option value (optval) is a pointer to an integer: 

• Non-zero value: enables the option. 

• Zero value: disables the option. 

• optlen is set to sizeof(int). 

## Example:

The option must be set before calling bind(). 

# Sockets: Options SO_REUSEADDR

## Context:

After a TCP connection is closed, the endpoint performing the active close typically enters the TIME_WAIT state for a limited period. 

• TIME_WAIT helps prevent delayed packets from an old connection from interfering with a new connection. 

• Connections in TIME_WAIT may prevent a new socket from binding to the same local address and port. 

• SO_REUSEADDR allows the address and port to be reused, subject to operating system rules. 

## When is it useful?

• When restarting a TCP server shortly after it has been stopped, bind() may fail with Address already in use. 

• Enabling SO_REUSEADDR can allow the server to restart without waiting for old connections to expire. 

Note: SO_REUSEADDR does not normally allow two TCP servers to listen on the same IP address and port simultaneously. 

## Sockets: Options SO_REUSEADDR

## Four-way termination

After sending the final ACK, the endpoint initiating the close enters the TIME_WAIT state. 

TIME_WAIT serves two purposes: 

• Allows retransmission of the final ACK if the peer retransmits its FIN. 

• Allows delayed segments from the old connection to expire before the same connection identifiers are reused. 

The connection remains in TIME_WAIT for a limited period.

## Sockets TCP: Buffer

• The size of this buffer can be configured using the SO_SNDBUF socket option. 

• If the available buffer space is smaller than n bytes: 

• Blocking socket: write() waits until all requested bytes are accepted into the send buffer. It may return fewer bytes if interrupted or if a send timeout occurs. 

• Non-blocking socket: write() never waits for buffer space. It may immediately return a partial byte count or EAGAIN/EWOULDBLOCK. 

• In both cases, write() may return fewer bytes than requested. Its return value indicates the number of bytes accepted for transmission, not necessarily delivered to the receiver. 

• The default behavior is blocking.

## Sockets TCP: Buffer

• When read() is called with n bytes on a TCP socket, the kernel attempts to copy up to n bytes from the socket's receive buffer into the application's buffer. 

• If fewer than n bytes are available: 

• Blocking socket (default): read() normally returns the available bytes without waiting for the buffer to fill. If no data is available, it blocks until data arrives, the connection is closed, or an error occurs. 

• Non-blocking socket: read() returns immediately with the available bytes, or -1 with EAGAIN/EWOULDBLOCK if no data is available. 

• The return value indicates the number of bytes actually read. A return value of 0 indicates that the peer has closed its sending side and all pending data has been read. 

• The default behavior is blocking

Each TCP socket has two kernel-managed buffers: 

• Send buffer: temporarily stores outgoing data received from the application before transmission. 

• Receive buffer: temporarily stores incoming data before delivery to the application. 

Their sizes can be configured using: 

• SO_SNDBUF: send buffer size. 

• SO_RCVBUF: receive buffer size.

• SO_SNDBUF: a larger buffer can queue more outgoing data, potentially reducing blocking in send(). 

• SO_RCVBUF: a larger buffer can accommodate more incoming data, reducing the risk of TCP flowcontrol stalls.

## Multiple Connections on the Same Port

A TCP server can handle multiple simultaneous connections using a single listening port. 

• The server creates a listening socket using socket(), bind(), and listen(). 

• Each accept() returns a new connected socket, listening socket remains available for new connections. 

• All connected sockets share the same local server port. 

Each TCP connection is uniquely identified by a 4-tuple: (Source IP, Source Port, Destination IP, Destination Port) 

The number of connections is limited by system resources, not by the listening port alone. 

Which one? 

# Limits on Concurrent Connections

A TCP server can handle many simultaneous connections on the same port, but the number is not unlimited. 

## The main limitations are:

• File descriptors: Each connected socket requires a file descriptor. Operating systems impose perprocess and system-wide limits. 

• Kernel memory: Each TCP connection requires control structures and send/receive buffers. 

• CPU resources: Managing many active connections increases processing overhead. 

Client source ports: Connections from the same client IP to the same server IP and port require distinct source ports (16-bit port numbers). 

• Server architecture: A process-per-client or thread-per-client model consumes more resources than event-driven I/O multiplexing. 

Note: Source port exhaustion limits connections from a particular client IP to a specific server endpoint, not the total number of connections a server can accept.

## Socket: multicast

When an application joins a multicast group, the operating system and the network cooperate to manage multicast communication. 

## How does it work?

 Group membership: the receiver uses IP_ADD_MEMBERSHIP to request membership in a multicast group. 

 Operating system: the OS manages the membership request and communicates the necessary information to the local network. 

 Network: multicast-aware routers can use group membership information to forward packets towards networks with interested receivers. 

 Data delivery: the sender sends UDP datagrams to the multicast IP address, without knowing the individual receivers. 

Key idea: socket options allow applications to request network-level behaviors, while the underlying network handles packet delivery. 

We will explore how group membership and multicast forwarding work when we study the network layer.

• As just shown, we can create sockets between two hosts, but we need to know (IP) address and port of the server. 

• On the Internet, hosts are typically identified by hostnames rather than by IP addresses. 

• Berkeley sockets (C/C++) only works with IP addresses. 

• This is not surprising as sockets works on transport layer, while hostnames works on application layer. 

• If we are to connect with a host by hostname, we need to use DNS translation and get the associated IP address to be passed to the socket. 

## Application Layer DNS Translation

• C/C++ offers some functions and structures that perform such translation for us, which are used to contact DNS servers and to retrieve addresses. 

• gethostbyname() is a legacy function used to resolve hostnames into IPv4 addresses through the system resolver. 

• The above function does not return just the IP address. It returns a hostent structure that contains some info about the host: 

• Canonical name. 

• Possible aliases. 

• One or more addresses. 

For new applications, getaddrinfo() is recommended, as it supports both IPv4 and IPv6.

## Transport Layer Congestion and Flow Control

There is one field of the header we have never used, and one limit that is in no header at all: 

• The receive window says how much room is left in the buffer at the other end: a limit set by the receiver. 

• The other limit is set by the network (congestion), which has to be guessed from what comes back. 

• Both end in the same action — send less 

• Reliability told us what to do after a loss. Nothing yet says how not to cause one. 

• And both end in the same place: the moment your write returns, or does not. 

## Transport Layer Congestion and Flow Control Problem

• Additional features of TCP with respect to UDP are the congestion and flow control. 

• Packet loss on the Internet is rarely a broken wire: it is often a result of buffers overflow: 

• From receiver buffer, if receiving application is not fast enough in reading the data. 

• From network devices (e.g., routers), if nodes are congested. 

• Following our previous water-flowing analogy, we can see buffers as intermediate buckets that overflows in case water exceeds. 

• If packets are lost, hosts are forced to rely on retransmission and timeouts that drastically impair the network performance.

# Transport Layer

## Flow Control

• When the TCP connection receives bytes that are correct and in sequence, it places the data in the receive buffer. The receiving application will read data from this buffer, but not necessarily at the instant the data arrive (application may be busy). 

• If the application is relatively slow at reading the data, the sender can very easily overflow the receiver buffer by sending too much data too quickly. 

• TCP flow control is a speed-matching service: it attempts to match (reduce) the rate at which the sender is sending against the rate at which the receiving application is reading. 

• In this case we rely on a receive window to inform the sender how many segments we can receive without producing overflows. 

• Remind: TCP segment allow receiver to tell the sender how much buffer has left through the receive window field (free buffer space). 

## Transport Layer Flow Control

• Let’s assume for simplicity that the TCP receiver discards outof-order segments, so all segments in the buffer are ordered. 

• On the receiver side (host B) we have: 

• RcvBuffer: size of the receiver buffer (in bytes) 

• LastByteRead: the last byte of the stream retrieved by the application. 

• LastByteRcvd: the last byte of the stream that is received. 

• We may define the size of the receive window (rwnd) as: rwnd = RcvBuffer – (LastByteRcvd - LastByteRead) 

• On the sender side (host A) we have: 

• the last byte of the stream to be sent. 

• the last byte of the stream that is acknowledged by the receiver. 

• Knowing the receive window, the sender guarantees anytime that: 

LastByteSent – LastByteAckd ≤ rwnd

## Transport Layer Flow Control

• The receiver puts its current rwnd in the receive window field of every segment it sends back. 

• The sender keeps two numbers of its own: LastByteSent and LastByteAcked. 

• Their difference is the data in flight — sent, and not yet acknowledged by anybody. 

• The rule: LastByteSent − LastByteAcked ≤ rwnd 

• Keep to it and the receive buffer cannot overflow: the sender never has more outstanding than there is room for. 

• The connection is full duplex, so each direction has its own window and each end announces one. 

![image](https://cdn-mineru.openxlab.org.cn/result/2026-11-19/5b0063d5-63a6-423f-96aa-ec44dd9d39f2/02463d5e59ab98c97dc243f7146c0c5311041efbe2d09a4b214339ef548e95c0.jpg)


B advertises rwnd = 0 and has nothing of its own to send. The application at B then empties the buffer (rwnd > 0). Who speaks first? 

Nobody. TCP sends a segment only when it has data or an acknowledgement to send, so the new window is never announced — and A, which may send nothing, waits forever. 

• The specification breaks the deadlock from the sender’s side: 

A keeps sending segments with one byte of data (zero-windows probes) 

• The receiver acknowledges them, and sooner or later, one of those acknowledgements carries a non-zero window.

## Flow Control

• Limitation: The TCP Window Size field is 16 bits, allowing a maximum advertised window of 65,535 bytes (≈ 64 KB). 

• Problem: A window is also associated with a speed limit — at most one windowful per round trip, so at most window/RTT. 

• 64 KB over a 100 ms RTT is about 5 Mbit/s, whatever the link underneath is worth. 

• Bandwidth-delay product: 1 Gbit/s over that same RTT is 12.5 MB in flight: two hundred times the field. 

• Solution: TCP Window Scaling allows larger receive windows: the window scale option carries a shift count, the number in the field is not the window: it has to be shifted. 

• Negotiation: each endpoint announces its scale factor (S) during the TCP handshake. The factor remains fixed throughout the connection.

## Congestion Problem

• Flow control is an agreement between the two ends. The network is not party to it and does not appear in it. 

• But the path is shared: a sender can be well inside the receiver’s window and still be putting in more than the path carries. 

• Nobody says so. Routers send no complaint, and neither end can see the queue that is filling up. 

• Two questions: what does congestion actually cost, and how can a sender find out that it is happening? 

• The first is answered by three scenarios, and the answer is worse each time. 

# Transport Layer Congestion Problem

• The congestion control problem is similar to flow control, but it is related to the network infrastructure. 

• Example: two hosts (A and B) have a connection that shares a single router and a single outgoing link of capacity between source and destination. 

![image](https://cdn-mineru.openxlab.org.cn/result/2026-11-19/5b0063d5-63a6-423f-96aa-ec44dd9d39f2/de451fe4ea27e94e109e808367d996ce009f61801512892d85985a0d376e9c02.jpg)


• The router has buffers that allow it to store incoming packets when the packet-arrival rate exceeds the outgoing link’s capacity. 

• Link capacity: R bytes/s 

Let’s assume for simplicity that both applications (in A and B) are sending data into the connection at the same average rate of λin bytes/s. 

## Transport Layer Congestion Problem – simplified view

• If λin<R/2, everything sent by the sender is received by the receiver with a finite delay. 

• If λin=R/2, the link reaches its full capacity (R), and the exceeding packets are stored into the buffer. 

![image](https://cdn-mineru.openxlab.org.cn/result/2026-11-19/5b0063d5-63a6-423f-96aa-ec44dd9d39f2/7d82ba848cc1f84e9b72a5acab481c010c3293e7064920e02ee7c98b4bc8b0c4.jpg)


• As long as we exceed the maximum capacity the packets will be accumulating into the router’s buffer waiting for their turn to be sent into the link. 

• Since the buffer is finite, accumulated packets will eventually be discarded, and hosts will be forced to retransmit them (even more traffic). 

• An infinite buffer doesn’t work either: packets will not be lost but the delay would constantly increase: if we exceed the capacity forever, the delay will reach infinity (so packets are as good as lost).

## Transport Layer Congestion Problem – Finite buffers

• If λin<R/2, everything sent by the sender is received by the receiver with a finite delay. 

• If λin=R/2, the link reaches its full capacity (R), and the exceeding packets are stored into the buffer. 

Buffers are finite, so a packet arriving to a full one is dropped, the connection is reliable: what is dropped is sent again.

λ′in: the offered load: original data plus retransmissions, which is what the link actually sees.

• (a) No packet losses: All transmitted data is successfully delivered, achieving a maximum throughput of $\mathsf { R } / 2$ per connection. 

• (b) Retransmission of lost packets: Buffer overflows cause packet losses. Retransmissions consume network resources, reducing useful throughput.

## Transport Layer Congestion Problem – Multihop Networks

Four senders transmit data over overlapping two-hop paths, competing for the routers' limited buffer space and link capacity: 

Wasted resources: A packet may cross the first router but be dropped at the second, wasting the bandwidth already used. 

• Increasing congestion: As the offered load grows, more packets are dropped before reaching their destinations. 

• Congestion collapse: Under extreme congestion, useful throughput can decrease towards zero, even while the network remains heavily loaded. 

![image](https://cdn-mineru.openxlab.org.cn/result/2026-11-19/5b0063d5-63a6-423f-96aa-ec44dd9d39f2/ddd80bb6a1612f860bd3ecc1b400e0085fd780e401fa6a65b805309b11b6b7cd.jpg)


Key takeaway: More transmitted traffic does not always mean more delivered data. This motivates the need for congestion control. 

Historical note: Congestion collapse was observed in the Internet in the 1980s, motivating the development of TCP congestion control mechanisms. 

• There are mainly two approaches to congestion control: 

1. End-to-end congestion control: this is the standard TCP approach where congestion is inferred by the end systems based only on observed network behavior (for example, packet loss and delay). 

• TCP segment loss (due to timeouts or the receipt of 3 duplicate ACKs) is taken as an indication of network congestion, and TCP decreases sending rate accordingly. 

2. Network-assisted congestion control: this is a recent (optional) approach where transport-layer works in synergy with network-layer. Routers provide explicit feedback to the sender and/or receiver regarding the congestion state of the network. 

• The CWR and ECE flags are used to this end. 

• The feedback may be as simple as a single bit indicating congestion at a link, but more sophisticated feedback is also possible. 

# Transport Layer Congestion Control

## Network-assisted congestion control: Explicit Congestion Notification (ECN)

ECN allows routers to signal congestion without necessarily dropping packets. 

• ECN-capable transmission: The sender marks IP packets as ECN-capable using the 2-bit ECN field: 00 Not-ECT; 01 ECT(1); 10 ECT(0); 11 CE 

• Congestion detection: A congested router can mark a packet with CE (Congestion Experienced) instead of dropping it. 

Receiver feedback: The receiver sets the TCP ECE (Explicit Congestion Notification Echo) flag in its acknowledgements to report congestion. 

• Sender reaction: With classic TCP ECN (using ECT(0)), the sender reduces its congestion window, upon receiving an ACK with the ECE flag set, and sets the CWR (Congestion Window Reduced) flag to acknowledge the reduction 

CWR: TCP Reno - 50% reduction 

Key takeaway: ECN allows TCP to react to congestion without requiring packet loss, reducing unnecessary retransmissions. 

## Transport Layer Congestion Control: Network-assisted

## 1. ECN negotiation (TCP TCP)

• ECN support is negotiated during the TCP three-way handshake using the ECE and CWR flags in the TCP header: 

• SYN: ECE = 1, CWR = 1 (ECN requested). 

• SYN-ACK: ECE = 1, CWR = 0 (ECN accepted). 

• This negotiation establishes that both TCP endpoints support ECN. 

## 2. ECN marking (TCP IP within each host)

• Once ECN is negotiated, the sender's TCP requests the IP layer to mark outgoing data packets as ECNcapable (ECT(0) = 10). 

• TCP and IP communicate through internal operating-system interfaces, not through additional network messages. 

• At the receiver, the IP layer informs TCP when a packet is marked CE = 11, allowing TCP to generate ECE feedback. 

Note: ECN negotiation is standardized in TCP; TCP–IP interaction is implementation-dependent. The ECN field itself belongs to the IP header. 

## Transport Layer TCP Congestion Control

• TCP mostly relies on end-to-end congestion control. 

• The approach is to have each sender to adapt their sending rate depending on the perceived network congestion. 

• Here there are 3 main problems to be considered: 

• Sending Rate Control: how does a TCP sender limits the rate at which it sends traffic into its connection? 

• Congestion detection: how does a TCP sender detect the congestion on the path between itself and the destination? 

• Congestion Response: what algorithm should the sender use to change its send rate as a function of perceived end-to-end congestion? 

Note: senders are not coordinated. Each acts on local information, asynchronously.

## Transport Layer TCP Congestion Control –TCP Sending Rate and Self-Clocking

• The TCP sending rate is approximately determined by the congestion window and the round-trip time: 

$$
\mathrm{Sendingrate} \approx \mathrm{cwnd/RTT}
$$

## Example

Congestion window: cwnd = 10 MSS, with MSS = 1,000 bytes 

Round-trip time: $\mathsf { R T T } = 1 0 0 \mathsf { m s } = 0 . 1 $ s 

The approximate sending rate is? 

$$
\begin{array}{c} \text {Sending rate = 10 MSS / 0,1 = 10000 / 0,1 = 100000 byte / s =} \\ \text {800kbit / s} \end{array}
$$

## Why is it approximate?

TCP does not explicitly set this rate. It controls the amount of unacknowledged data through cwnd, while ACK arrivals determine when new data can be sent. 

The formula estimates the average sending rate, assuming cwnd is fully utilized and RTT is relatively stable. 

## Transport Layer TCP Congestion Control – Congestion Detection

• A TCP sender perceives that there is congestion on the path between itself and the destination in two ways by checking loss events. 

• A loss event happens when either a timeout is reached or 3 duplicate/wrong ACKs are received. 

• Both events mean that a previous packet is not arrived at the destination probably because of network devices overflow. 

• If loss events do not occur, i.e., ACKs of segments arrive as expected, TCP will assume that network is not congested, so the congestion window can be increased. 

• If, on the other hand, loss events occur, the congestion window must be decreased. 

## Transport Layer TCP Congestion Control –Bandwidth Probing

Classic TCP adjusts its congestion window (cwnd) based on network feedback: 

• ACK received: Successful delivery allows cwnd to increase. 

• Packet loss: Congestion is assumed, so cwnd is reduced. 

• Bandwidth probing: TCP repeatedly increases cwnd until congestion is detected, then backs off. 

• Main mechanisms: Slow Start, Congestion Avoidance, Fast Retransmit and Fast Recovery. 

# Transport Layer TCP Congestion Control –Slow start

cwnd starts at 1 MSS: with a 500-byte MSS and a 200 ms path, about 20 kbit/s. Far too little, and the sender has no idea by how much. 

It grows by one MSS for every segment acknowledged, and a round trip brings back as many acknowledgements as there were segments. 

So the window doubles every round trip: 1, 2, 4, 8. Linear in acknowledgements, exponential in time — what is slow is the starting point, not the growth.

# Transport Layer TCP Congestion Control – slow start, where does it end?

During Slow Start, cwnd approximately doubles every RTT, until one of three events occurs: 

• Timeout: ssthresh (Slow Start Threshold) is set to cwnd/2, cwnd goes back to 1 MSS, and restrat slow start. 

• cwnd reaches ssthresh: Switch to Congestion Avoidance: linear growth. 

• Three duplicate acknowledgements: Trigger Fast Retransmit and enter Fast Recovery (TCP Reno). 

ssthresh: determines when TCP switches from exponential to linear growth and is updated in response to congestion.

## Transport Layer TCP Congestion Control – Congestion Avoidance

When cwnd reaches ssthresh, TCP switches from exponential to linear growth. 

Window growth: Approximately 1 MSS per RTT. 

Per-ACK increase: ���� $\begin{array} { r } { \mathrm { ~  ~ \omega ~ } + = \ M S S \ \cdot \ \left( \frac { M S S } { c w n d } \right) = \frac { M S S ^ { 2 } } { c w n d } } \end{array}$ 

Example: With cwnd = 10 MSS, each ACK adds approximately 0.1 MSS, resulting in about 1 MSS per RTT. 

Takeaway: TCP probes for available bandwidth more cautiously than during Slow Start. 

## Transport Layer Classic TCP Congestion Control (Reno) – Fast Recovery

Triggered by 3 duplicate ACKs, indicating a likely packet loss. 

• Fast Retransmit: Immediately retransmit the missing segment. 

• Window adjustment: Set ssthresh ≈ cwnd/2 and cwnd = ssthresh + 3 MSS. 

• Additional duplicate ACKs: Increase cwnd by 1 MSS per duplicate ACK. 

• Recovery complete: When an ACK acknowledges new data, set cwnd = ssthresh and resume Congestion Avoidance. 

• Timeout: Reset cwnd to 1 MSS and restart Slow Start. 

Key idea: Recover from packet loss without restarting Slow Start.

## Transport Layer TCP Congestion Control – Rate Adjustment

• TCP rate adjustment is then performed through bandwidth probing: rate is increased as long as ACKs arrive correctly (probing the network), when congestion is detected (loss events) the rate is decreased. This process is continuously repeated. 

• TCP uses Jacobson congestion-control algorithm [Jacobson 1988, 1990] to regulate the rate, it includes 3 phases: 

1. Slow start: start from 1 MSS cwnd increase rate exponentially. 

2. Additive Increase (or congestion avoidance): increase rate linearly. 

3. Fast Recovery: After 3 duplicate ACKs, TCP retransmits the missing segment and reduces cwnd without restarting Slow Start.

## Transport Layer TCP Congestion Control – Rate Adjustment

TCP Reno provides the basic model, but modern systems may use different congestion control algorithms. 

• Tahoe: Resets cwnd to 1 MSS after packet loss, restarting Slow Start. 

• Reno: Introduces Fast Recovery, avoiding Slow Start after 3 duplicate ACKs 

• CUBIC: Uses cubic cwnd growth during Congestion Avoidance. Default in Linux. 

• Vegas: Uses RTT variations to detect growing queues. 

• BBR: Estimates bottleneck bandwidth and propagation delay to regulate the sending rate. 

Key takeaway: Different algorithms aim to efficiently utilize available bandwidth while limiting congestion and delay. 

## Transport Layer Summary — TCP Flow and Congestion Control

• Flow Control: Protects the receiver's buffer using the advertised receive window (rwnd). 

• Congestion Control: Protects the network by adjusting the sender's congestion window (cwnd) based on network feedback. 

• Congestion Costs: Queuing increases delay; packet losses and retransmissions waste network resources. 

Classic TCP Reno: Slow Start increases cwnd exponentially, Congestion Avoidance increases it linearly, and Fast Recovery avoids restarting after 3 duplicate ACKs. 

• Sending Limit: The amount of unacknowledged data is limited by min(cwnd, rwnd).
